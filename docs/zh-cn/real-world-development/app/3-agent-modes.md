我们先为项目添加了一项小功能，但更大的更改需要更完善的流程。GitHub Copilot app 可配合组织现有的工作流程，帮助我们用正确的方法构建正确的内容。从本课开始，你将通过几节课遵循典型的代理驱动开发流程：根据 issue 构建新功能、确认代码有效且功能按预期运行，最终成功将更改合并到项目中。

> [!NOTE]
> 在后续功能工作流中，你将使用同一个会话。通常，不同类型的文件会使用不同会话或 PR；此处为聚焦核心概念会简化流程。

本课将介绍如何：

- 从 GitHub issue 启动新的代理会话。
- 在 **Plan** 模式下确定需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续实现此功能时，你还将更新存储库说明、自定义现有的 quality-checks 技能、添加 MCP 验证、创建 QA 代理并打开功能 PR。

## 场景

Tailspin Toys 的目录不断扩大，访问者需要按类别和发行商筛选游戏。待办 issue 描述了该功能，但多个类别如何组合等细节需要在编码前达成共识。你将使用 Plan 模式确定这些决策，然后授权 Autopilot 在明确范围内实现功能。

## 背景

将 AI 编码代理引入开发流程不会改变基本原则。事实上，这些原则反而更加重要！大多数开发人员遵循的流程大致如下：

1. 打开描述待办事项的现有 issue。
2. 制定要构建内容的计划。
3. 构建并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码通过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程都是以上主题的变体。

坚持这种标准方法，可以确保 AI 生成的代码满足既定要求，并经过与手写代码相同的审核流程。

## 会话模式

**会话模式**控制代理的自主程度。可以通过提示框下方的下拉列表设置模式，并随时更改：

- **Interactive**：你与代理协作。代理提出更改建议，并等待你的输入后再继续。
- **Plan**：代理先制定计划。你审查并批准计划后，代理才会执行。
- **Autopilot**：代理完全自主工作，包括编写代码、运行测试并不断迭代，无需等待输入。

先在 Plan 模式下审查计划，然后使用 Autopilot 实现。

## 从 issue 启动会话

开始之前，确认星级评分 PR 已合并，并且本地 `main` 已更新。

1. 在侧边栏的 **Sessions** 下，选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是已预先创建的 issue，无需再创建一个。
2. 选择 **New session**，并选择基于更新后 `main` 的 **new working tree**。

    ![GitHub Copilot app 的 issue 视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认 issue 已附加到会话，并在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让代理运行 `node --version` 和 `npm --version`。如果它们在终端中可用，但在会话中不可用，请检查应用的 PATH 或版本管理器设置，然后完全退出并重新打开应用。重试失败的操作和检查；不要仅因为代理找不到 npm 就重新安装 npm。

## 规划筛选功能

规划让你可以在 Copilot 编写代码前审查实现方案。由于会话从 issue 启动，Copilot 已获得功能请求的上下文。发送：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并对照 issue 的验收标准审查计划。确认计划涵盖按类别和发行商筛选、无障碍控件、数据访问更改和测试。讨论不明确的行为，例如多个类别如何组合，或没有匹配游戏时会发生什么。

计划应使用项目现有工具运行 lint、单元测试、E2E 测试和类型检查。将计划限定为实现和测试筛选功能；完成质量工作流后再创建 PR。批准之前先要求修改计划，并保留 issue URL 和已商定的澄清内容，以供后续验证。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中的等效选项。不要假定批准后会自动切换模式；请确认活动模式指示器显示 **Autopilot**。

Copilot 会开始实现功能！你会看到它按既定计划逐步工作、生成代码并运行测试。

> [!NOTE]
> 批准后可能会立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再将检查视为已完成。只停止自己启动的服务器。

## 审查并验证实现

生成的代码在合并前需要审查，就像其他代码一样。现在审查代码并运行网站，确认一切正常。

1. 打开 **Changes**，检查筛选实现和测试。
2. 对照 issue 和已批准的澄清内容检查结果，包括多个类别和发行商组合。确认更改遵循现有存储库说明。
3. 检查 lint、单元测试、E2E 测试和类型检查的输出。跳过的检查不能算通过。
4. 接受实现前，解决失败项并重新运行受影响的检查。Playwright 的 E2E 配置会构建并提供预览服务，也可能复用本地服务器；确认被测服务器属于此工作树，而不是之前课程启动的服务器。

## 试用新功能

代码看起来没问题，但实际运行如何？像之前一样启动应用，并在浏览器画布中打开网站。

1. 使用以下提示让 Copilot 启动应用，并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 稍等片刻，应用将启动，Copilot app 内会打开浏览器窗口。
3. 选择一个类别，确认结果与该类别匹配。清除筛选后，再选择发行商并确认结果与该发行商匹配。
4. 同时设置类别和发行商筛选，并根据 issue 和已批准的计划核对结果。如果支持多个类别，还要验证已商定的组合行为。
5. 尝试一个没有匹配游戏的组合，检查空状态。清除或重置筛选条件，确认完整列表会重新显示。
6. 完成后，使用以下提示让 Copilot 停止为此会话启动的开发服务器并关闭浏览器画布：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 保留此会话以供后续课程使用

暂时不要创建或合并筛选 PR。第 4 到第 8 课会继续使用此会话、工作树和分支。接下来会将自定义说明应用到筛选代码，然后添加技能和 QA 改进，最后在第 8 课创建并合并合并后的 PR。停止开发服务器后，可以让会话保持空闲，并在下一课返回同一会话。
